About this simulation

Meridian Analyst is a showcase MVP of AI-supported immersive learning, built for the Silverse × Regent Business School pilot. A student manages {{ pack.currency }}{{ pack.starting_capital | int }} of a client's money across a fictional South African share market over {{ pack.total_rounds }} quarterly rounds: read the brief, forecast, allocate, see explainable results, get live AI coaching, reflect, repeat.

How it's set up

The whole app is one small FastAPI service rendering server-side Jinja pages, with htmx for the live fragments (allocation totals, AI coaching, the lecturer cohort view) and a single SQLite file for state. It runs with one command — docker compose up --build — and serves on http://localhost:8010 (host 8010 maps to the container's internal 8100).

  • Offline by design. Dependencies install from a vendored wheelhouse and the frontend libraries (htmx, Chart.js) are vendored too, so a build and a demo never depend on the network — no PyPI, CDN, or DNS hiccup can stall a live session.
  • Self-seeding. On first boot the database creates demo accounts plus a fictional completed cohort, so the leaderboard and lecturer view look alive before the first live playthrough. A presenter runs python -m app.seed reset to restore clean state between groups.
  • Cookie-session auth. A signed cookie carries the logged-in user; each browser/device is an independent session, which is what lets many testers play at once through a single shared URL.

Decisions that shape the experience

  • Outcomes are deterministic and explainable. A pure simulation engine computes every price move and score, and each carries a plain-language "why". The AI never invents an outcome or a number.
  • The AI coaches; it never grades. The system prompts forbid stating or changing any score, and every score in the app comes from the deterministic model. Coaching is grounded strictly in the student's own decisions and the rule-based results.
  • The demo can't stall. Live AI calls have a 10-second timeout with one retry, then fall back to authored, pre-approved content — so a slow or absent API is invisible to the student.
  • Student free text is treated as data. Reflections and rationales are wrapped in a delimited block with a treat-as-data instruction, so a "rate this 100" can't steer the model.
  • Deliberately throwaway. Shared credentials, no password hashing, one SQLite file — good enough to prove the value of the pilot without carrying the pilot's engineering obligations.

Making it flexible: more simulations, richer AI feedback

The architecture already separates what the simulation is (the content pack) from how it runs (the engine, scoring, and feedback services). That separation is the growth path.

1. A library of simulations, not one market

A scenario is a single validated YAML file: title, currency, starting capital, number of rounds, a client and mandate, a set of shares with per-round prices and rationales, market briefs, and authored fallback text. Point CONTENT_PACK at a different file and you have a different simulation — no code change. From here we can:

  • Author a catalogue of scenarios (a volatile market, a recession quarter, an ESG-tilted mandate, a bond-heavy conservative client) and let a lecturer assign one per cohort.
  • Vary length and difficulty — more rounds, more shares and sectors, tighter mandates — all from the pack, since the engine validates and adapts to whatever the pack declares.
  • Generalise beyond finance. The same forecast → decide → explainable-result → reflect loop fits operations, marketing spend, supply-chain, or public-sector budgeting cases; only the content and the scoring weights change.
  • Add a lightweight authoring/validation UI so subject-matter experts write packs without editing YAML by hand — the loader already fails loudly on malformed content, which is the hard half of that feature.

2. Deeper AI feedback

Feedback lives behind one small interface (round_feedback, reflection_prompt, rate_reflection) with an authored fallback always behind it. That makes richer coaching a contained change:

  • History-aware coaching. Today each round is coached on its own facts. Feeding the student's full trajectory (trust trend, repeated mistakes, whether they act on prior advice) lets the coach notice patterns and growth across the whole run.
  • Per-share and forecast-vs-outcome tutoring — call out exactly where a forecast diverged from what happened and why, tied to the deterministic "why" each price already carries.
  • Adaptive difficulty and Socratic depth. Use the indicative reflection rating to decide when to probe harder or offer a hint, nudging without ever touching the score.
  • Richer, still-safe grounding. The grounding + treat-as-data + always-fallback pattern generalises — new prompts can pull in more context while keeping the guarantees that outcomes stay deterministic and the AI never grades.
  • Multi-turn debrief. A short back-and-forth at the end of a run, letting the student ask the coach "what should I have done in round 2?" grounded in their real decisions.

3. Scaling the platform

For a real cohort the same shape scales cleanly: swap SQLite for Postgres via DATABASE_URL, add real accounts and roles, and cache or queue AI calls. None of that touches the simulation logic — which is the point of keeping content, rules, scoring, and coaching as separate, swappable pieces.

Synthetic market — not investment advice. All companies, prices, events, and the client are fictional.
